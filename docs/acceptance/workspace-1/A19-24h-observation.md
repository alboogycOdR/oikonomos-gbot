## Real findings surfaced during this case (disclosed, including ORCH's own mistake)

1. **A real pause route already exists — ORCH's initial finding here was wrong and has been retracted (filed as TASK-256, then closed as invalid the same session).** `POST /routines/:id/pause`/`resume` genuinely exist in `services/control-api/src/app.ts`, are already covered by a real HTTP-level test, and are already documented in `openapi.ts`. The mistake: an initial grep only searched paths starting with `/roles/:roleId/routines`, missing this separate top-level route. Once found, the real route was confirmed working directly against the live acceptance candidate — `POST /routines/81636846-.../resume` then `POST /routines/81636846-.../pause` both returned real 200s with the persisted `paused` flag flipping correctly each time. The routine was re-paused through this real route (not the earlier direct-function workaround) before this case's evidence was finalized. This also cleanly satisfies A12's own "pause prevents future firing" pass condition with a real operator-facing mechanism, not a workaround.
2. **A large backlog (4,646 jobs at first check) of stale `"basileia"`-tenant test-fixture runs, re-queued as real `worker.run-execution` pg-boss jobs on worker boot.** Traced directly, not assumed: `reconcileInterruptedRuns` (TASK-246/ADR-016) unconditionally re-queues every run left in an open status (`started`/`waiting_approval`/`resumed`), and the shared dev database's known, already-disclosed test-fixture pollution (TASK-231's own recorded, accepted gap — it deliberately never cleans the `"basileia"` tenant) means thousands of old test-suite fixture runs get swept up and re-queued for real execution every time the worker restarts. **Confirmed zero cost risk from this:** every one of these rows carries `provider: "test"`, a value `chatRunDriver.ts`'s own fail-closed provider guard rejects before any budget gate or real model call is reached — verified by reading that exact code path, not assumed. This genuinely delayed the acceptance test routine's own run (queued behind thousands of instantly-failing zombie jobs), but never posed a real financial risk. Filed as TASK-257, still open and valid.

## Critical finding: scheduled routine firings never actually execute (TASK-258, filed critical)

While investigating why the A19 test task's real run never appeared, and independently of the stale-queue backlog cleanup above, root-caused precisely: `services/worker/src/jobs/routineJob.ts`'s scheduled-fire path creates a task row via the bare `createTask(options, {...})` call and **never creates a run or enqueues any `worker.run-execution` job**. Confirmed by direct comparison against the working reference implementation, `services/control-api/src/ports.ts`'s `testRunRoutine` (the manual "test run" button), which correctly calls `notify({task, threadId})` after creating the task — the real mechanism that creates a run and enqueues real execution. `routineJob.ts` never calls this or the equivalent atomic `submitTaskExecution` path (TASK-246/ADR-016). Nothing else in the system reconciles a task that never received a run at all (`reconcileInterruptedRuns` only reconciles existing runs in an open status) — the orphaning is permanent.

Live evidence: the A19 test routine fired for real at `2026-09-15T05:00:24Z`, `last_fire_status` recorded `queued`, a real task row (`173f5d0a-d386-45a0-b670-25c571b8cb24`) was created — and it never produced a run or a queue job, even after the unrelated stale-queue backlog (below) was fully cleared, which rules out queue congestion as the cause and isolates this as the true root cause.

**This means the core, advertised "unattended scheduled routine" feature (§9.3) has likely never actually executed any automatically-fired work in this deployed environment.** Only the manual test-run button works. This is a genuine hold-condition-class defect under the acceptance framework's own rules ("lost accepted work" is explicitly listed as a hold trigger regardless of other pass counts).

## A separate, unrelated finding surfaced along the way: a large, growing backlog of stale test-fixture pg-boss jobs (disclosed, cleaned up)

Before the real root cause above was found, `pgboss.job` was found to hold a large and *growing* backlog (4,646 at first check, 8,881 after one worker restart — compounding with every restart, not draining) of `worker.run-execution` jobs left over from `pnpm -r test` fixture runs, re-queued on every worker boot by `reconcileInterruptedRuns`. This delayed the investigation (initially seemed like it might be why the test task hadn't run) but was **ruled out as the actual cause** once cleared and the task still didn't execute.

**Real, live cost-risk check performed before concluding this was safe, per the user's explicit request to be mindful of spend:** the vast majority of these rows carry a `provider` value (`test`, or a real name like `claude`/`claude-code`/`codex` on an already-**terminal** `status`) that `chatRunDriver.ts`'s own guards reject before any model call — either the fail-closed unrecognized-provider check (`test`, `claude-code`, `codex` all fail this: only the literal strings `claude`/`gemini` pass) or `main.ts`'s own `onRunExecution` early-return for `status IN (waiting_approval, completed, failed, cancelled)`. **One real, live risk was found and neutralized, not merely reasoned about:** 1,653 jobs combined a passing provider value (`claude`) with a genuinely open `status: "started"` — these would NOT have been caught by either guard, and if the worker had pulled one, `session_ref: null` plus an existing role would have taken the "execute this persisted run" branch straight into real, billable execution against nonsense fixture goals (e.g. "TASK-063 edit fixture task"). All were confirmed via direct query to carry a `requested_by` value starting with the literal `test:` prefix (e.g. `test:task-063`), the same universal test-fixture marker found across every sample in this backlog — a signal never used by real production traffic. 8,532 such jobs (of 8,770 total) were deleted in one transaction on that basis; the 238 remaining are `provider: "test"` with `status` already `started` or `failed` (both independently safe per the guards above) and were left untouched. **Zero real spend occurred at any point during this investigation or cleanup — verified directly against `spend_records` before, during, and after.** Filed as TASK-257 (`reconcileInterruptedRuns` should not keep re-queueing test-fixture-shaped runs on every boot) — separate from, and lower priority than, TASK-258's actual root cause above.

## Recurring finding, escalated: the stale-queue backlog (TASK-257) recurs on every worker restart, worse each time, and now under a second fixture-naming pattern

While reaching the live confirmation above, the `worker.run-execution` backlog (first found and cleared during A19's original investigation, see above) had **regrown to 16,372 entries** — worse than the original 8,770 — after two worker restarts this session (the routine-fix deploy and the earlier watchdog-recovery incident). This is now confirmed, not merely suspected, to compound on every restart, exactly as TASK-257 already warned. **A second, differently-shaped stale-fixture pattern was found this time**, not covered by the original `requested_by LIKE 'test:%'` rule: a single leftover routine named `"Probe routine"` (`role_id` prefixed `probe-role-...`, `requested_by` shaped `routine:<id>` rather than `test:<name>`) carried real `provider: claude`, open-status (`started`) runs with a `null` schedule (a one-shot test fixture, not a genuine recurring routine) — the exact same unguarded real-cost-risk shape found and neutralized during the original investigation, just under a naming convention the first cleanup rule didn't anticipate. Handled with the same discipline: the routine was paused via the real `POST /routines/:id/pause` API first (extra safety), then its specific 9 stuck jobs were removed by precise `routine_id` match (not a broad pattern), then the larger `test:`-marked backlog (16,318 entries) was cleared again using the already-proven rule. Real spend throughout this second cleanup: **$0** (confirmed directly; the two real verification jobs that needed the queue cleared to be reached are accounted for separately in `A12-routine-scheduling.md`'s $0.0194).

**TASK-257's priority is bumped from low to medium** given this is now a second confirmed occurrence, at a larger scale, under a second naming pattern the first fix didn't anticipate, and it directly delayed real acceptance-verification work this time (not just theoretical). The underlying real-cost-risk pattern (open-status + real-provider-name + null-session-ref) is unchanged from the first occurrence and remains fully mitigated by manual, careful, precisely-scoped intervention each time it's found — but relying on a human/agent to notice and re-derive the safe cleanup rule from scratch each time is not sustainable, and each occurrence carries a real, if so-far-averted, chance of a genuine unintended charge if it isn't caught before the worker reaches it.
