  With a genuine tie in place, the strengthened test still failed against the **unmodified, review-approved-as-clean production code** — not a test bug. Root cause: `encodeTaskCursor` builds the pagination cursor from `row.created_at.toISOString()`, a millisecond-precision JS `Date`, while the `created_at` column is microsecond-precision `timestamptz`. Confirmed by direct SQL probe (`docker exec ... psql`): a row with true `created_at` `...028120+00` produces a cursor timestamp of `...028Z` (`.028000`), which is strictly *earlier* than the row's real value — so the next page's `(created_at, task_id) < (cursor.createdAt, cursor.taskId)` filter excludes that row (and any other row sharing its millisecond bucket) from every subsequent page. This is a real, previously-undetected pagination bug, not limited to exact ties — any two rows whose `created_at` values are within the same millisecond (routine under fast/batched task creation) are at risk of one silently vanishing from `listTasks`/`listRuns` output. Fixed by selecting `created_at::text AS created_at_cursor` (Postgres's own lossless text form, round-trips exactly through `::timestamptz`) server-side and building the cursor from that instead of the parsed `Date`; same fix mirrored in `runs.ts`'s `listRuns`/`encodeRunCursor` (`started_at::text`), which has the identical pattern — not separately flagged by review, but same territory (`Owned_Paths`), same root cause, and `runs.test.ts`'s own pagination test had the identical untested-tiebreaker gap, so I strengthened it the same way rather than leave a matching latent bug in the sibling function.
