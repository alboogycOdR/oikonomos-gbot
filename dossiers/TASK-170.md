- [2026-09-06T16:20:00Z] [ORCH] DOCKER-USER firewall step (README §7.1) is now genuinely applied and independently verified — this was NOT a simple apply-and-done: the README's own documented remedy (`iptables -I DOCKER-USER ... --dport 30000:30999 -j DROP`) was fundamentally broken since it was written (2026-08-16), for every host, not just this one. Root cause (confirmed via full `sudo nft list ruleset` dump): Docker's `nat/PREROUTING` DNAT rewrites the destination port to the container's real internal port (e.g. `44772`) BEFORE `filter/FORWARD` (where `DOCKER-USER` lives) ever sees the packet, so matching on the published port `--dport 30000:30999` there can never fire — the port that number described no longer exists on the packet by the time the rule is evaluated. This was never caught earlier because the port band's prior "closed" observation (README §7, 2026-08-16) came entirely from the separate, upstream Hetzner cloud firewall, not this local rule, which had simply never been live-tested against real container traffic until this task's own live proof needed it. Fixed with `-m conntrack --ctorigdstport 30000:30999` (matches the pre-NAT original destination port, which conntrack preserves) instead of `--dport`. Verification chain, each step independently confirmed rather than trusted: (1) local packet-counter check showed 0 hits even after real connections succeeded — caught the bug; (2) full `nft list ruleset` dump showed the DNAT-before-FORWARD ordering directly; (3) after the corrected rule, the local counter showed real hits (8 packets); (4) an independently-run online port-checker (from South Africa, unrelated to any of this session's own infrastructure) confirmed the port went from `open` to `filtered`; (5) the persisted `/etc/iptables/rules.v4` file was confirmed to contain the corrected `--ctorigdstport` rule, not the old broken one.
